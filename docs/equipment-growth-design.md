# 装备无限升级的稳定性方案

基于当前英烈v1.0.2维护分支。以下先记录已落地的第一阶段，再保留后续迁移设计。

## 第一阶段实现

- Magnitude是非负科学计数类型：独立指数、定长尾数、明确零值，提供加减乘、比较、指数增长和Bundle保存恢复。拒绝NaN/Infinity。超过约16个数量级的微小加减会被舍弃，这是浮点尾数精度政策；它不是任意精度整数。
- 戒指指数增长接入EquipmentGrowth/Magnitude。旧返回接口仍是float，采用显式有限转换边界，最高Float.MAX_VALUE；生命、伤害等旧字段仍未完整迁移。故本阶段不是“全部战斗已无限大数化”，INT_MAX血量止血上限依旧存在。
- 极速/狂怒保留倍率<=8的原始曲线，高等级平滑趋近64倍；诅咒速度对称处理。实际正耗时角色行动限制在1/64到64回合。零耗时事件和有限负耗时退款保留。能量倍率限制在1/1024到1024，等待后续独立平衡。
- Actor内部使用TurnTime定点刻度，每回合1048576刻度，正的微小时间至少1刻度，取消近整数舍入。内部排序不依赖float；同时间同优先级按ID稳定排序。旧float时间读取，新存档追加time_ticks_v1并保留旧显示字段。
- 连续32次“act返回继续、仍在调度集合、时间不前进”的同一Actor被安排到至少1/64回合之后，只记录一次保护日志；不重新调用已执行动作，不重放动画回调。每128次调度或4毫秒让出CPU约1毫秒；中断继续走原生命周期。
- 此保护不保证任意act内部循环可恢复，也不会强杀线程；保护推迟异常Actor会改变其异常执行顺序。GameScene的10秒移动等待恢复仍保留。
- Wand.gainCharge改为按缺少的容量直接结算，Infinity直接满充，NaN/非正新增量忽略；不逐点循环。
- 戒指读档直接恢复等级及限制，再恢复显式状态，不逐级重放升级；其他装备的恢复仍待分别审计。等级增加/减少和多戒指加成合并增加溢出边界保护。
- 巨大增长的百分比使用科学计数显示；速度和充能说明显示实际受控倍率。

源码验收：`python tools/numeric_regression.py`使用完整当前Actor源代码与最小依赖桩，验证零耗时抢占保护、停用Actor排除、旧/新时间存档；使用完整新类型验证巨大指数、零乘法、致死减法、科学计数存档；抽取真实Wand.gainCharge验证无限充能终止。`boss_regression.py`和`health_regression.py`仍需持续通过。完整Android构建及模拟器结果另记录于numeric-stability.md。

## 确认的风险链

1. Item.level及Ring.getBuffedBonus使用int；多戒指叠加、等级+1和诅咒等级转换都有溢出入口。升级等级只是输入，主要风险在下游公式。
2. 极速1.2^bonus、狂怒1.105^bonus、命中1.3^bonus、闪避1.15^bonus、根骨1.035^bonus、能量1.2/1.15^bonus、财富1.2^bonus、神射耐久1.2^bonus均直接转float。
3. Actor.spend在时间小数部分小于0.001时舍入到整数。基础耗时1、当前时间0时，极速有效bonus38、狂怒70已经把正耗时变成0，远早于float倍率溢出。
4. Java探针按现有公式复现：极速bonus37耗时0.0011756929，38为0；狂怒69耗时0.001018598，70为0。bonus1000两者倍率均为Infinity。Infinity乘0为NaN。
5. MMO.damageFactor内部把指数伤害转回int，血量和攻击管线也保留int/float。只把戒指返回值改成大数，仍会在战斗边界截断。
6. Item.restoreFromBundle对正等级调用upgrade(level)，后者逐次执行upgrade；高等级读档的工作量随等级增长。不能直接改成level(value)：武器、防具等升级有附魔、铭文、封印等副作用，需专门的恢复路径。
7. Wand.Charger.gainCharge的while只判断partialCharge>=1；Infinity或大到减1不变的有限float会让循环无法终止。常规Charger.act有curCharges<maxCharges上界，不能把两者混为同一个漏洞。
8. MMO额外掉落amount随sqrt(MMO.modifier())增长，然后逐个创建实体。财富的普通掉落倍率用于概率而非同倍率实体数量；财富奖励循环另有零随机间隔、被屏蔽物品重试和高等级装备恢复的风险，不能声称财富倍率直接生成指数数量物品。

## 推荐引入有明确用途的类型

### Magnitude：生命、伤害、护盾和数值防御

使用非负尾数与独立指数，例如1.2345×10^1494，零有明确表示。定长有效精度，计算量不随完整十进制位数增长；指数采用有检查的整数表示，仍有有限范围，不能声称数学上无穷。

统一实现加减、乘法、指数倍率、比较、随机范围、比例和序列化。禁止自动转int/float；只有UI比例、概率等明确边界可以转换。相减前比较：伤害>=剩余HP时直接归零并走正常死亡，避免人为Math.max(1,...)制造残留1血。数量级差过大时舍弃微小加减必须是明确的精度政策，并测试接近致死阈值的减法。

数值类型不负责决定护盾、无敌或保命：这些仍由战斗机制处理。根骨倍率和MMO倍率以对数或指数构造Magnitude，不能先调用Math.pow溢出后再包装结果。乘减伤也必须留在同一数值链中。

### Rate / Probability：命中、闪避、减伤与掉率

命中和闪避的成长权重可保存在对数域。不要把Infinity交给Random.Float，也不要用不存在的“无限闪避”表示合法数值。显式无敌、必闪和必中保持独立机制，规定冲突优先级。

可以保留原双方独立均匀随机对抗的分布，同时在对数域比较：log(accuracy)+log(U1)与log(evasion)+log(U2)，随机数必须在开区间(0,1)，并处理零权重。直接改成accuracy/(accuracy+evasion)是另一种命中分布，只能作为重新平衡的选择。

减伤用剩余伤害倍率，不先计算“100%-免伤百分比”；多个倍率累加对数并作用到Magnitude。显示时接近100%要显示剩余倍率，避免舍入为100%却仍受到正常伤害。神射耐久、掉率与充能各有容量/概率边界，不属于无限实体数。

### TurnCost：回合耗时

角色行动必须消耗正的可表达时间；同刻回调、初始化及需要零耗时的事件用单独接口，不能把全部spend(0)一刀切改成消耗一回合。

单纯精确表示10^-7918仍然允许一名角色在敌人一个回合内行动10^7918次。必须同时限制实际行动速度的增长，建议低等级保留原曲线，高等级平滑接近可玩的倍率上限。具体上限要通过Boss/群怪体验验证，暂不擅自固定。

超过速度收益区间的升级仍可提升攻击威力、连击收益或资源效率；这些是玩法选择，不是类型系统自动推出的结果。角色看起来仍很快，但不能要求调度器实际执行天文数量的微回合。

调度还应有每帧处理预算、持续让出渲染线程、检测行动后时间不前进。预算耗尽只延后继续处理，不丢弃回合、不强行清除Boss状态；它只能保持界面可响应，不能替代增长曲线调整。

## 戒指处理清单

| 戒指 | 主要迁移方向 |
| --- | --- |
| 根骨 | 最大HP使用Magnitude，按新旧上限变化补血；治疗、灵药、护盾全链路迁移 |
| 极速、狂怒 | 正耗时规则、速度软上限、调度预算；高升级额外收益另设计 |
| 命中、闪避 | 对数权重比较，保留或显式调整命中分布 |
| 韧性、元素 | 依伤害来源计算剩余倍率，在Magnitude伤害链应用 |
| 能量 | 按缺少的充能量直接结算，满充停止，不逐单位循环 |
| 财富 | 概率和奖励质量增长；批量结算、实体生成预算与有限重试 |
| 武力 | 裸拳伤害范围迁移Magnitude，避免随机int范围溢出 |
| 神射 | 伤害升级并入武器成长；耐久收益单独表达，避免Infinity计数 |

## 实施顺序和验收

第一步先修正速度/充能的可终止性，并为装备恢复建立不重放升级副作用的路径。这比先改HP字段更直接解决卡死。

第二步引入Magnitude，按伤害→减伤→护盾→剩余HP→死亡→治疗→Boss阈值的闭环迁移。旧int字段不能作为新数据的权威镜像；版本化存档读旧格式、写新格式，迁移前备份。Boss阶段门槛、血条、伤害浮字、经验奖励、回血效果和状态持续时间逐个审计。

第三步统一武器、防具、戒指、怪物的成长尺度。大数只保证数值能算，不能解决怪物指数成长而武器防具线性成长的问题。保持刷取数量、奖励质量和装备成长的爽感，同时批量保存奖励，限制同帧实体创建。

建议测试等级0/10/30/100/1000/100000，负等级及诅咒，两枚同类戒指，读档与卸装；测试调度必前进、充能循环有界、生命非负、致死归零、同量不同攻击来源结果一致（明确机制例外）、治疗不反向扣血。Android实际复测仍必须关闭不死，覆盖天狗两阶段、国王及满场召唤。

## 类型选择

BigInteger可用于要求精确的整数计数；BigDecimal支持任意精度十进制但仍需明确精度和舍入，不能自动解决回合密度或实体生成量。推荐BigDecimal作为Magnitude测试的参考答案，对战斗热路径采用固定精度的科学计数类型。实际性能优劣须测量，不能把BigDecimal一概判为不可用。
